### 三个关键坑（重要，别再踩）
1. **`AlphaBlend`/`GdiAlphaBlend` 在本机（沙箱会话，无真实显示适配器）静默失败**，
   GetLastError=87 或 0，返回 FALSE。后果是玻璃面板整片不可见 —— 上一版所谓
   "玻璃卡片"其实只有描边画出来了。**改为逐通道 LUT + `bytes.translate` 自建合成**
   （`Canvas.blend_rect/blend_round/panel`），像素级精确（±1）、更快、可验证。
   - blend_round 四角：先留存**原始**像素再按圆覆盖率混合，否则二次叠加；
   - 操作 `blk[a:b]` 这类切片副本必须把返回值写回，否则改动丢失（整行调用才生效）。
   - COLORREF 低位是 R 不是 B（`0x00BBGGRR`），LUT 取通道时别按字面当 B。
2. **`CreateFontW` 必须声明 `restype`**（用 `aurora.gdi32`，已带完整原型）。
   未声明时 ctypes 按 `c_int` 截断 64 位 HFONT → `SelectObject` 静默失败 →
   图标字体整片消失、中文回退成宋体。这正是上一版"难看"的主因。
   另：CreateFontW 共 **14 个参数**，别漏 `fdwPitchAndFamily`。
3. **GDI 家族名是 `Segoe UI Variable Text`**；裸的 `Segoe UI Variable` GDI 找不到会静默回退。

## 17:00 之后：圆角/置顶标识 + 一个致命的内存越界

用户反馈两点：①窗口列表右侧「又有圆角又有直边」；②置顶后列表右侧是否显示置顶标识。

### 圆角 bug 的根因（`Canvas.blend_round`）
`blk` 是**从 x=0 起的整行**切片，不是从 `x0` 起。四角裁剪时列号用了**相对列号**
(`0 / w-r_c`)，于是圆角被切到矩形中间去：顶边中间出现缺口、四个角反而还是直角。
→ 改成 `bx = x0 / x1-r_c`（绝对列号），圆心 `ccx = x0+r_c / x1-r_c`，
覆盖率按「像素中心 = 局部坐标 + 0.5」算（`cov = r_c + 0.5 - hypot(dx,dy)`）。
顺带把覆盖率表按半径缓存（四角对称，共用一张表）。

### 置顶标识
原来只在行右侧画了一个 13px 图钉字形，太细太淡几乎看不见。
改为「图钉 + 置顶」胶囊徽章（品牌色淡底 + 1px 品牌色描边，右对齐，宽 68 高 22），
标题/进程名给它让出宽度。已用**真实窗口**跑通端到端：`set_topmost(True)` →
`is_topmost` 为真 → 行标记 `r[4]` 为真 → 徽章区域采到品牌色像素。

### ★ 致命 bug：`BeginPaint` 的 PAINTSTRUCT 缓冲区太小（既有 bug，非本次引入）
`ontop.py` 的 `on_paint` 里 `ps = ctypes.create_string_buffer(64)`，
但 **x64 下 `PAINTSTRUCT` 是 72 字节**（hdc 8 + fErase 4 + 对齐 4 + rcPaint 16
+ fRestore 4 + fIncUpdate 4 + rgbReserved 32）。`BeginPaint` 每次多写 8 字节，
**踩坏相邻 Python 堆块** → 运行十来秒后在完全无关的地方随机崩溃
（faulthandler 报的位置漂移：`_toolbar` 的 genexpr / `_row` 的 DrawTextW）。
- 用 **`PYTHONMALLOC=debug`** 一次抓到：`bad trailing pad byte`，
  块内容 `0e 05 01 65` 正是 PAINTSTRUCT 的 hdc 字段 → 4/4 稳定复现。
- 修法：声明真正的 `PAINTSTRUCT` 结构体（`sizeof == 72` 已断言），
  `BeginPaint/EndPaint.argtypes` 换成 `POINTER(PAINTSTRUCT)`，用 `ctypes.byref(ps)`。
- 复检：`PYTHONMALLOC=debug` 下 4/4 通过；`--shot` 6/6 通过；
  正常消息循环 25 秒 539 帧、调试分配器下 15 秒 319 帧均无崩溃。
- 教训：**凡是把 Python 缓冲区交给 Win32 API 写的，缓冲区尺寸必须按 x64 真实
  结构体算，宁可声明结构体也不要用 `create_string_buffer(猜)`。**

### 顺带的性能优化（视觉等价，已逐像素校验）
- `panel()` 原本「整块铺描边色 + 内缩 1px 铺填充色」= 两倍面积；
  合并为一次等效叠加（A = 1-(1-a1)(1-a2)，C·A = c1·a1·(1-a2)+c2·a2）
  + `blend_round_ring()` 只描 1px 圆环。新旧像素最大通道差 1~4（两主题 6 组半径），
  892x506 面板 9.53ms → 7.64ms。
- `_apply_rect()` 按宽度分档：整行宽一次 translate；**单列**用扩展切片
  （`blk[s::stride]`，之前 660 行的 1px 边框要走 660 次逐行切片）；
  较宽则整行 translate 后还原左右边距；较窄才逐行。
- 整窗绘制 33.5ms → 27.2ms/帧。
- 另修：`ui.py` 里每行都 `ctypes.WinDLL("comctl32")` 重新绑定且无 argtypes
  （HIMAGELIST 会被截断）→ 改为模块级带完整原型的绑定。

### 其他

## 18:10 CI/Release 机制修正：固定标签的 release 看起来"永远没更新"

用户反馈"我仓库没有最新的 release"。排查：
- **代码是推送成功的**（`origin/main` == 本地 HEAD，工作区干净）；
- 但 CI 用的是固定标签 `tag_name: latest` + `softprops/action-gh-release`：
  资源确实每次都换新（`assets[].created_at` 是当天），**可 GitHub release 列表
  显示的是「首次发布日期」**，所以页面上那条 "Latest build" 永远停在 2026-09-04，
  看上去像没更新。另外 `latest` 标签的 ref 还指着旧 commit（c644f2b）。
  → **教训：滚动发布不要复用固定标签，否则日期不动、看不到"新版本"。**

改法（`.github/workflows/build.yml`）：
- 触发加 `push.tags: ['v*']`；`checkout` 加 `fetch-depth: 0`（要读全部标签）。
- 新增 `Resolve version` 步骤：推 `v*` 标签时直接用标签名；main 推送时取
  `git tag -l 'v[0-9]*.[0-9]*' --sort=-v:refname | head -1` 再加 1
  （`v2.1` → `v2.2`），输出到 `steps.ver.outputs.tag`。
- `Publish release` 用这个版本号建**新 release**，资产名保持
  `AlwaysOnTop.exe` / `AlwaysOnTop_v2.exe` 不变，`releases/latest/download/...`
  这类链接依然有效。
- 实测：推送后 CI 53 秒跑完，自动生成 `v2.2`（tag → c68da16，published 当天），
  `releases/latest` 已指向 v2.2。
- 顺带验证：用 PAT 把 `releases/download/v2.2/AlwaysOnTop.exe` 拉下来
  （7,520,186 B，MZ 头正常）→ 直接运行 `--shot` 出图正常，
  且恰好列表里有个真实置顶窗口，右侧「图钉+置顶」徽章显示正确。

遗留：旧的 "Latest build"（tag `latest`）release 已不再更新，成了历史条目，
可按需删除（未擅自删）。

补充：加了 `paths-ignore: ['.workbuddy/**', '**.md', '.github/workflows/**']`，
纯文档/记忆/工作流改动不再发新版本（避免"改个 README 就多一个 release"）。
已验证：仅改工作流那次推送没有产生新的 run。另外把一次 docs 提交误触发的
构建用 `POST /actions/runs/{id}/cancel` 取消了，没留下多余的 v2.3。
注意「路径过滤对 tag 推送不生效」，所以推 `v*` 标签一定构建；
改完工作流要验证就用 workflow_dispatch 手动跑。
